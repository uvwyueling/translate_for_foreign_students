## 实现取舍与尚待验证的假设

- 字幕的中英文配对使用翻译响应自带的 `src` / `dst` 和开始偏移 `wb`；独立中文识别显示为当前草稿。需要实测 `wb` 在同一句修订中是否稳定。
- 识别使用 `sn`、`pgs` 与 `rg` 做修订，并在 `sub_end` 后清空当前句。需要用真实响应确认分句和修订跨句行为。
- TTS 请求 raw PCM。真实接口短测发现：`id` 随音频块变化，`seq` 在每段 `status=2` 后重置。后端已改为按段内 `seq` 有序实时转发，传到浏览器的序号在整个连接内持续递增，不再按 `id` 聚合或等待整句。该规则已加入回归测试；多次重复、长课堂和现场播放仍需继续验收。
- 后端待排序语音不超过约 30 秒 / 64 块，缺片超过 12 秒明确报错；前端待播不超过 60 秒；上行超过 2 秒网络缓冲触发重连，不积攒离线课堂音频。
- 模拟语音使用浏览器 speech synthesis；尽量选择本机英语 voice，具体语音可用性、输出设备与播放授权必须人工检查。模拟语音时长为词数估算，真实 PCM 时长由采样数计算。
- 当前字幕延迟是以供应商结束偏移匹配浏览器收到 PCM 帧的时刻近似计算，未校正音频设备缓冲。尚未建立可靠的 TTS 与输入片段映射，所以没有声称测得真实英文起播延迟。
- 连接默认 240 秒主动交接，不能保证无损；交接时清除未播语音，明确提示重述关键句。自动交接尚未利用句间静音优化。
- 暂停及结束立即关闭浏览器会话；后端发送结束帧后关闭上游。未完成翻译的尾句可能丢失，迟到结果不得继续播放。
- 服务业务错误默认停止自动重试，避免未知鉴权或额度错误不断消耗资源。网络级断连最多五次指数退避；成功连续运行 30 秒后重置计数。
- 字幕窗口每 2 秒请求同步，教师页面也发送心跳。未收到状态超过 6 秒显示失联；同步仅限同浏览器同源，不支持跨电脑。
- 不实现数据库、音频保存、字幕历史导出、术语库和 PPT 内容读取。

## 点击开始后立即讲话丢掉句首

2026-10-18，用户在线上点击“开始课堂”后立即说“今天我们要学习中国的在地文化。”，字幕只留下“文化。 / Culture.”。

- 已确认的代码缺陷：前端先开启麦克风，再连接网页 WebSocket 和讯飞；旧 `sendFrame` 在收到 `ready` 前直接返回，连接前已采到的声音没有上传或暂存。用户确认立即讲话，符合只收到后半句的表现。没有该次原始录音，不能精确还原具体丢失秒数。
- 用同一句固定合成中文（约 3.23 秒）在连接就绪后发送至真实停顿送译链路，返回的最终中文包含开头“今天”和末尾“文化”，完整句子保留在同一条字幕；无服务错误。本次没有复现 `wb` 标识覆盖，不据猜测改动字幕分句逻辑。讯飞字段定义参见[官方协议](https://www.xfyun.cn/doc/nlp/simultaneous-interpretation/API.html)。
- 已修复：开始 / 继续时短时缓存已经采到的音频，上限 300 帧 / 12 秒 / 384 KB；收到 `ready` 后与新帧一起按原顺序、40 ms 节奏上传。缓存满则明确报错并停止，不截掉句首后继续翻译。字幕延迟仍以原采集时间计入，避免隐藏启动等待。
- 暂停、结束、失败、断线会清空缓存与发送定时器；重连期间仍不补传旧内容。采音回调增加本次启动标识检查，阻止旧回调混入恢复后的课堂。
- 麦克风授权 / 初始化完成之前的讲话无法恢复。连接前已经讲话会增加暂存等待，因此页面提示等到“课堂进行中”后开始讲课。
- 本地修复不等于 Vercel 已更新；线上需要部署修复后再验证。真人麦克风与线上复测尚未完成。

## 真实语音无声排查

- 用户已确认：本地真实同传有中文字幕和英文字幕，字幕延迟可接受；英文试听可听，但真实同传无声。
- 使用固定合成中文 WAV 做短测（不是用户麦克风录音），真实服务返回 40 个音频块、260480 字节 PCM；旧解码器输出 0 个播放事件，复现无声。
- 原因：旧代码将每块变化的 `id` 当作句子标识，导致队首块始终没有等到同一 `id` 的结束状态。现按实测段内 `seq` 与结束状态恢复流式转发。
- 首轮修复后 `npm run check`：构建与 23 项自动化测试通过。真实接口复测：返回 42 个 TTS 事件，其中一个为空音频结束标记，产生 41 个播放事件（28 个在输入结束前发出），解码错误及服务错误均为 0；用户侧扬声器复测尚待确认。
- 排查本地运行日志还发现页面关闭时向已关闭的字幕同步通道发送消息。已修正释放顺序和重复清理，并增加回归测试。
- 最终构建及 24 项自动化测试通过。本地服务已加载修复，等待用户刷新页面后确认真实英文声音。
- 排查脚本 `scripts/probe-live-audio.ts` 仅在人工运行时使用真实 API，会消耗额度；只输出计数、块长度和协议元数据，不记录语音载荷、识别正文或凭证。

## 语音延迟优化

- 用户确认真实英文可听，但每一句起播等待较长，尚无秒数记录。
- 已将网页 PCM 播放改成依据音频时钟连续排程；不再依赖每个块的 onended 回调启动下一块。暂停与结束会取消所有已排程声音，保留 60 秒待播上限。
- 增加“最近音频的网页排队等待”数字及导出汇总，辅助区分网页积压与云端等待，不声称它代表完整声音延迟。

## 根据实际计时增加语音对比模式

- 用户五句测试约 7、7、7、4、7 秒，待播基本为 0；第 4 句首词后停顿约 0.5–1 秒。中位数约 7 秒，尚不能认定适合实时课堂。
- 新增可选的“本机朗读英文字幕（对比测试）”，默认仍为讯飞语音。新模式只朗读已确认且未朗读过的片段，过滤讯飞音频，避免两路同时播放。中间字幕和已播句子的修订不重复朗读。
- 新模式先检查本机英语语音，声音列表异步加载时等待至多 1.5 秒；缺少时在采音和连接前停止并提示，不隐式改用远程朗读。课堂中不能切换声源，暂停或结束后可切换；重连重新建立语音序列。
- 字幕仍由真实讯飞同传服务生成，同一服务可能仍生成云端语音；新模式不是免费或离线翻译，也不据此宣称降低调用用量。
- 本次仅做自动化回归，未代用户调用真实 API；实际是否降低延迟、Mac 与 Windows 声音效果需要下一轮同句对比。

## 本机朗读对比仍约 7 秒：补充计时

- 用户报告五句均约 7 秒，没有观察到英文字幕出现时间。按本机朗读对比上下文记录，等待运行数据确认模式与阶段耗时；尚无改善证据。
