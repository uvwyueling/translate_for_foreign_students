# 英文声音延迟测试

本地真实服务已经能够播放英文。此次优化将网页 PCM 播放改为音频时钟连续排程，减少每个小块等待主线程播放结束回调的额外间隙。没有设置加速播放，也不自动跳过课堂内容。实际改善幅度须通过以下步骤验证。

## 手动测试：先分清生成等待与播放积压

1. 结束课堂、刷新页面，选择真实同传，输入课堂口令，打开“运行数据与排查”。
2. 第一轮说短句，例如“今天我们学习中国文化。”。**说完最后一个字时开始计时，听到对应英文的第一个词时停止。** 记录两者的时间差，不从开始说中文时计时，也不等英文播完。
3. 用手机秒表即可粗测；同伴操作秒表更方便。无需录音，也无需上传文件。
4. 在开始说话前记录待播时长，待播接近零后再开始。不要为了每句计时反复清空队列，因为清空会重建云端会话、引入交接影响。
5. 等上一句英文播完，再换一句短句。测 5 次，保留每次数据。若英文在中文结束前已经开始播放，记为“提前开始”，不要误记成等待 0 秒或补造精确负值。
6. 第二轮连续说约 1 分钟，观察待播秒数是否持续增长，再记录末句的延迟。

| --- | --- | --- | --- | --- |
| 1 | 待测 | | | |

| 5 | 待测 | | | |

“最近音频的网页排队等待”表示最近一个音频块到达网页后，按音频时钟计划等待多少时间才开始播放。它可能属于句中其他块，不能直接当作所计时句子的等待值；不含云端处理、网络和声卡输出。它用于辅助判断积压，不代替手动端到端计时。

- 待播与网页排队接近零，但每句仍需等：重点检查供应商分句、翻译、合成与网络返回时间。
- 连续说话时待播不断增长：生成的英文播放速度跟不上讲述，需要继续评估讲述节奏、语速或其他语音服务方案。
- 字幕很快但音频晚到：字幕与合成语音是不同输出，字幕出现并不代表音频已经返回。

默认“讯飞英文语音”由同一条流式同传会话返回字幕和音频。另有“本机朗读英文字幕（对比测试）”：收到最终英文字幕后交给本机英语语音朗读，只读一次，不等待或播放讯飞返回的音频。没有安装可用的本机英语语音时明确提示，不自动改用远程语音。它仍使用讯飞同传服务，不代表不消耗讯飞额度，也不承诺一定更快。

## 用户第一轮实际结果

2026-10-17，用户按五个固定短句手动计时，报告如下。均为近似值，不包含独立录音或精确对时。

| 样本编号 | 中文句尾到英文首词 | 播放表现 |
| --- | --- | --- |
| 1 | 约 7 秒 | 整句连贯 |
| 2 | 约 7 秒 | 整句连贯 |
| 3 | 约 7 秒 | 整句连贯 |
| 4 | 约 4 秒 | 首个词后停顿约 0.5–1 秒，再继续 |
| 5 | 约 7 秒 | 整句连贯 |

用户观察待播时长基本为 0。样本中位数约 7 秒，均值约 6.4 秒，范围约 4–7 秒。该结果不支持“持续播放积压是主要原因”的判断；更可能是音频到达前的云端处理或网络等待，但目前没有分阶段精确计时，不能进一步精确归因。

下一轮在停止课堂后切换“英文声音来源”为“本机朗读英文字幕（对比测试）”，用同样五句、同样语速、同样句尾到首词方法计时，并留意是否连贯。此方式等待最终字幕而非中间字幕；若最终字幕本身很晚，本机朗读也未必改善。

## 本机朗读对比结果与下一步定位

用户随后报告五句英文声音延迟均约 7 秒，未注意英文字幕出现时间。按上一轮本机朗读的测试上下文记录，尚无导出数据再次确认模式。对比未显示延迟改善，因此不能认定换朗读方式已解决问题，也不能据此单独确定供应商合成是瓶颈。

已增加两项自动数字计时：

- “英文字幕首次出现→确认”：同一片段首个非空英文文本到最终字幕；若服务首次返回的就是最终结果，此值为 0，不表示云端处理没有等待。
- “确认→本机朗读启动”：从该确认字幕到该条朗读触发浏览器 start 事件。包含本机队列和语音启动等待，不等于扬声器物理发声时间。

同时修正本机语音等待期间的时长显示：尚未触发 start 时，不应按墙钟时间把待播时长提前减到 0。只有真正开始朗读后才递减估算时长，因此之前“待播为 0”仍不能排除本机语音启动等待。

下一轮无需再手动测五遍：刷新后选择真实同传与本机朗读，展开运行数据，读一至两句并等英文播完，结束课堂后下载数字运行数据。数据包括所选模式和上述分阶段数字，不含音频、字幕或口令。若有两句，界面两项“最近值”可能来自不同片段，不能直接相加；导出汇总也不代替句尾到首词的人工测量。

## 定位到字幕返回之前：停顿送译实验

用户进一步观察：“化”说完到英文字幕约 7 秒，字幕出现与英文声音同时发生。这一人工观察将主要等待定位到英文字幕返回之前，切换声音来源没有显示改善。

用同一句固定合成语音进行两次真实短测，以 RMS 阈值估算最后有声帧的上传时间（约 40 ms 粒度，非物理麦克风句尾）：

| 条件 | 句尾上传→首个英文 | 句尾上传→首个音频块 |
| --- | --- | --- |
| 持续上传尾部静音，等待服务分句 | 6.700 秒 | 6.774 秒 |
| 句后较早发送 status=2 结束帧 | 0.964 秒 | 1.037 秒 |

结束帧仅表示当前上游音频结束，不是可在同一会话反复发送的“标点”。因此新增可选“停顿后尽快送译（实验）”，默认仍为连续同传：

- 在后端逐帧计算 RMS，累计至少 120 ms 有声后，连续约 800 ms 静音则发送结束帧。
- 保留旧连接直至收到最后结果，不清空已返回的字幕或音频；收完后新建下一条上游会话。对浏览器保留连续的音频序号，字幕标识添加上游分段编号。
- 连接交接期间保留最多约 6 秒 PCM，按原节奏上传；等待期间有新讲话时保留，不用无提示丢弃换取低延迟。空闲时最多保留约 200 ms 前导静音；超出缓冲、连接或结果等待上限明确停止或重试。
- 根据每帧对应的原始时间，将上游字幕偏移映射回浏览器输入时间，避免重开会话后延迟统计混用时间基准。
- 本机或讯飞两种声源都可配合使用。建议先选“讯飞英文语音”，减少对比变量。

随后用新实验流程连续发送两遍同一固定合成短句，中间留 2 秒静音，自动完成两段会话。第一、二段句尾上传到英文返回分别为 0.975 / 1.216 秒，到首个音频块分别为 1.067 / 1.298 秒；共 24 个音频块，没有服务错误。这是后端合成样本短测，不包含真人麦克风、浏览器播放和扬声器延迟，不保证课堂达到相同秒数。

请刷新后，在真实同传中设置“分句方式”为“停顿后尽快送译（实验）”，声音来源选择“讯飞英文语音”。先测试一两句，再测带正常句内停顿的长句以及连续讲话。RMS 阈值在教室噪声、轻声和较长句内停顿下可能误分句；必须检查漏字、跨句关系与翻译完整性。频繁开会话的账号限制与长课稳定性仍待验证。

## 真人短句复测结果

2026-10-17，用户在停顿送译实验后的短句测试中报告英文声音延迟约 1.75 秒，并表示满意。按前述句尾到对应英文首词的测试上下文记录；未提供样本总数与逐句数据，不能视为长句、持续讲述或 45 分钟课堂的延迟保证。

下一阶段保持当前设置，依次检查：正常语速长句的完整性、约 1 秒句内停顿是否切断因果或转折、约 1 分钟连续讲述的待播增长与重复漏句。长句英文可能在中文结束前开始，不能将长句最后一字到整段首个英文的差值当作同一片段的端到端延迟。

## 用户长句观察与本轮收尾

用户随后报告：从说完长句句末关键词，到听到对应英文关键词，约 11 秒；当前体验认为可接受。此项为尾部关键词跟随时间，不与短句英文首词起播时间直接比较。

用户决定结束本轮个人主导的延迟计时，后续正式时间延迟测试交由真实教师使用课程内容试讲完成。不要仅为继续调参要求用户重复同类计时；后续试讲应同时考察准确率、断句完整性、跟随延迟和持续积压。
